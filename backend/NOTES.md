# NOTES — Dataset Request Desk backend

## Design

### Data model

Five tables, all UUID-keyed, with FKs everywhere:

```
users 1──N requests 1──N assignments N──1 episodes (unique episode_id → 0..1 current assignment)
              │  1──N request_status_history N──1 users (changed_by)
              └── assignments.assigned_by ──> users
```

- **State lives in `requests.status`** — a Postgres native enum
  (`submitted/in_progress/delivered/accepted/rejected`), so no arbitrary
  strings can be stored. The transition map and the role that owns each
  target status live in one place (`app/services/request_service.py`), never
  in route handlers.
- **The audit trail is `request_status_history`** (from, to, who, when,
  optional reason). Creating a request writes the first `submitted` row;
  that row is also the `submitted_at` used by the median metric — no
  duplicated timestamp fields on the request itself.
- **Invariants are enforced by the database, not just code**:
  `assignments.episode_id` UNIQUE (one request per episode — also what makes
  the concurrency race safe), `episodes.episode_id` UNIQUE (idempotent
  imports), CHECK `duration_seconds > 0`, CHECK `episodes_requested > 0`,
  native enums for role/quality/status.

### Difficult decisions

1. **Where the workflow state machine lives.** It would have been fastest to
   scatter `if request.status != ...` through the endpoints. Instead all
   transitions funnel through `transition_request()`: map check → role
   check → delivery-rule check → status update + history row in one
   transaction. This is what the "role owns a step" rule (operator must not
   accept for a client) hangs off, and what made the transition tests easy.
2. **404 vs 403 for other clients' requests.** A 403 confirms the resource
   exists; a 404 does not. Clients get 404 on requests they don't own
   (list is scoped by `client_id` too). Operators/admins get 404 only for
   genuinely missing resources.
3. **Timestamps.** The CSV export has naive local timestamps (Kigali,
   UTC+2); Postgres columns are `timestamptz`. Decision: treat imported
   naive timestamps as UTC and store timezone-aware datetimes everywhere,
   and define analytics ranges as half-open `[from, to)` in UTC to avoid
   midnight-boundary ambiguity. A real deployment would pin the export
   timezone explicitly — documented as a simplification.

## Deliberate simplifications

- **Recordings live outside the system** — the brief only requires episode
  metadata; there is no upload/storage surface to attack or back up.
- **No unassignment endpoint.** The brief says deletion is optional and
  warns against convenience endpoints; the rework loop (rejected →
  in_progress) covers the operational need.
- **Background jobs (the stretch item) were skipped** in favour of a
  complete, tested core.
- **Sessions are stateless JWTs** — no refresh tokens, no revocation list.
  Deactivation stops a token at the next request (the DB is checked every
  call), but there is no "log out everywhere" mechanism. `jti` is already in
  the claims, so adding one later is mechanical.
- **Pagination is offset-based.** Keyset pagination would be the upgrade at
  real scale (see below).

## Something that went wrong

Alembic's autogenerated downgrade dropped the tables but left the Postgres
enum types behind, so a `downgrade base && upgrade head` cycle failed with
`CREATE TYPE episode_quality` (type already exists) — and my first
verification run "passed" because a `| tail` in the shell pipeline masked
the exit code. Diagnosed by re-running the downgrade with full output and
inspecting `pg_type`. Fix: the migration's `downgrade()` now drops the three
enum types explicitly; the up/down/up cycle is asserted in a real database.
The second-order lesson (never verify through `tail`) is why the test suite
now runs against real Postgres via Alembic rather than `create_all()`.

## Security

- **Passwords**: Argon2id via passlib; never stored or logged in plaintext;
  login returns the same generic error for unknown email / wrong password /
  deactivated account (no account-existence oracle).
- **Tokens**: short-lived HS256 JWTs from `JWT_SECRET` (env config; the app
  refuses to boot in `APP_ENV=prod` with the default secret). Tokens are
  never logged; the logging middleware records `user_id` from the resolved
  user, not the token.
- **Authorization**: every protected endpoint goes through the same
  dependency chain — resolve user → require active → require role →
  ownership scoping in the router/service. Verified by tests for every
  role/ownership combination, including a deactivated user with a still-
  valid token (403) and a forged-secret token (401).
- **Input validation**: Pydantic v2 models on every input (emails, enum
  statuses/qualities, positive counts, pagination bounds); SQLAlchemy
  parameterized queries only (no string-built SQL anywhere).
- **The two vulnerabilities I'd worry about most in this kind of system:**
  1. **Broken object-level authorization (IDOR).** A client calling
     `GET /requests/123` for someone else's request is the classic internal-
     tool breach, because IDs sit in URLs and frontends leak them. Mitigated
     by scoping every read/transition/assignment through
     `_scoped_request()` and returning 404 (not 403) for foreign resources;
     client lists filter by `client_id` at the SQL level. The risky variant
     is a *new* endpoint someone adds later that skips the scoping helper —
     that's what the ownership tests exist to catch.
  2. **Privilege escalation via the workflow.** If accept/reject were
     client-supplied "next status" without server-side role mapping, any
     client could accept its own request (or worse, an operator could
     accept), silently corrupting the audit trail. The state machine derives
     permissions from the *target status* (only clients may target
     `accepted`/`rejected`, and only on their own delivered request), so the
     server never trusts the caller's claim about what they're allowed to
     do. A client hitting the transition endpoint with
     `{"status": "accepted"}` gets 403 (or 404 when it isn't theirs).

## Scale

- **10x users:** fine on this single node; the first wall is the sync
  SQLAlchemy pool (5 + 10 overflow). Postgres comfortably handles the
  connection count; beyond that, add pgbouncer and/or move to async
  SQLAlchemy so worker threads aren't parked on DB I/O.
- **100x episodes (millions of rows):**
  - *Import:* the loader chunks (500 rows) and uses
    `INSERT ... ON CONFLICT DO NOTHING`, so it stays O(n) with no memory
    blow-up; the pre-check `IN (...)` lookups are index hits. A
    COPY-based path would be the next step for truly large files.
  - *Listing:* offset pagination degrades at deep pages — keyset
    (recorded_at, id) cursors would replace it; the indexes below are
    already in that shape.
  - *Analytics:* already aggregate in SQL with `GROUP BY` +
    `percentile_cont`, filtered by `recorded_at` bounds, so they scan
    ranges, not tables. At hundreds of millions of rows the per-day/robot
    group-by would move to a pre-aggregated rollup table refreshed on
    write or by a scheduled job.
- **Indexes** (chosen for the actual query patterns, documented rather than
  blanket-created): `episodes(episode_id) UNIQUE`, plus `robot_id`,
  `task_name`, `quality`, `recorded_at` for filters/ranges;
  `requests(client_id)`, `requests(status)`, `requests(deadline)`;
  `assignments(request_id)`, `assignments(episode_id) UNIQUE`;
  `request_status_history(request_id)`, `(changed_at)`;
  `users(email) UNIQUE`.

## AI tooling

AI assistants (Codebuff/Claude) were used as a pair-programmer throughout:
implementing routers/services/tests from the specification, debugging the
Alembic enum-type downgrade failure and a Pydantic `model_validate` misuse,
and drafting these documents. Every decision above, the test expectations
against the real messy CSV, and the architecture were human-reviewed; the
interview's live-session requirement is taken seriously — the code is
structured to be explainable line by line.
